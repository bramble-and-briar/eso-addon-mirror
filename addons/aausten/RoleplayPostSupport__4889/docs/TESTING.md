# Testing RoleplayPostSupport

Use these procedures for regression testing after changes. Checklist boxes are a reusable test plan, not a record of the author's completed in-game testing. The author's Tongues experience confirms ESO can preserve zero-width characters, not that the new v1.2.0 marker protocol has passed these checks.

Baseline: ESO **12.0.8 / API 101050**, `live` commit `f76cf16c4e5be7b234d15dc7f676febffa64c5bb` (**2026-08-10**; ESO `master` is stale); pChat **10.0.7.4**, `3a433e33fe8fcffbe24497374e4f98d75217eaef`. See [pinned API evidence](API-VERIFICATION.md) and [user workflow/privacy](../README.md).

## Standalone development checks (repository only)

The development repository includes `tests/run.py` and Lua specs for localization, the splitter, sessions, queue/chat adapter, UI, and bootstrap. These files are not included in the installed addon. The manifest [RoleplayPostSupport.txt](../RoleplayPostSupport.txt) stays in the repository root beside seven `RoleplayPostSupport*.lua` modules. It loads the bootstrap first, then `lang/default.lua`, optional `lang/$(language).lua`, the localization helper, and the existing five modules in their unchanged order (Splitter, Sessions, Queue, Chat, UI). From the repository root:

```sh
python3 tests/run.py
python3 tests/run.py tests/localization_spec.lua
python3 tests/run.py tests/queue_chat_spec.lua
python3 tests/run.py --syntax-only
python3 tests/run.py --lua lua5.1
python3 -m unittest discover -s tests -p '*_spec.py'
```

The Python tooling tests (Python 3.11+) verify manifest/load-order validation, root-source and catalog/documentation-subfolder paths, zip member mapping, symlink rejection, and runner source selection. Packaging includes actual optional two-letter locale files deterministically, never the literal `lang/$(language).lua` path or the user's local wiki HTML. The packager runs these alongside the Lua suites before building an archive.

`tests/localization_fixture.lua` mocks the real `ZO_CreateStringId`, `SafeAddVersion`, `SafeAddString`, and `GetString` API signatures and registry/version behavior, then loads the actual English catalog and localization helper. It supplies the localization dependency to standalone specs, including the splitter: the splitter has no chat/UI dependency, but is no longer independent of ESO string APIs. Do not execute editor declarations as test mocks or replace the real catalog with a hardcoded English helper.

`tests/localization_spec.lua` checks all 168 unique `RPS_` catalog keys at version 1, runtime key references, missing-locale and partial-override fallback, equal/newer overrides and older-version rejection, per-call lookup and fixture isolation, complete typed template formatting, and raw-data preservation (percent signs, newlines, Unicode, names/messages, markers, and wire tags). Synthetic overrides stay in test memory; they are not supplied translations. Existing bootstrap/UI/queue/chat/sessions specs exercise integration with the shared fixture.

The Lua runner syntax-checks root `RoleplayPostSupport*.lua` modules and actual `lang/*.lua` files, excluding the literal language placeholder, before executing specs in isolated Lua states/processes. It prefers an installed interpreter and can fall back to an installed shared library through Python's standard-library `ctypes`; it does not download dependencies. `--library` accepts an actual installed Lua library path or loader name. Record which runtime the runner reports. A pass on Lua 5.3/5.4 is not proof of Lua 5.1 compatibility; use 5.1 when available. These tests substitute ESO APIs and cannot validate a real client.

Inside ESO, `/rps test` runs a splitter-only smoke check with an artificial small budget. It must not prepare input or send anything. `/rps debug` toggles status diagnostics, including API/runtime limit and confirmed chunk indices, without logging message contents. Debug output is not a server delivery receipt.

## Temporary chat-tracking traces

Use this diagnostic build to compare a successful first batch with the next batch that stops advancing:

1. Install the updated addon and reload the UI before beginning the test.
2. Run `/rps debug` while no queue is active and confirm **Debug ON**. It is a toggle; if it reports OFF, run it again. The debug preference persists across reloads.
3. Send a short multi-chunk post normally with Enter, then start a second post with **different text**, without reloading between batches. Keep your usual chat addons enabled for the first reproduction.
4. When advancement stops, capture the `[RPS TRACE ...]` lines from the failed batch's `BATCH_START` through the `PAUSE` event and any following timer/timeout. Include the successful batch for comparison. Capture the failure before clicking recovery controls; if you then recover manually, include those traces too.
5. Record whether the Compose window was open, which channel type you used, which chat addons were enabled, and whether you clicked elsewhere or used Escape. Do not send private message text or recipient names.
6. After capturing the evidence, finish/cancel the queue as appropriate and toggle `/rps debug` off. Typing a slash command during a queue can itself alter native input and produce extra tracking events.

Traces go directly to **local chat output**, not to other players or an addon-managed file/archive. They do not refresh our UI or change the send/advance decisions. Other chat addons may retain local output; redact surrounding ordinary chat before sharing screenshots or copied logs. There is no automatic copying, upload, or file export.

A prefix such as `[RPS TRACE #0042 t=123450 B=2 C=1/3 G=8]` means event 42, frame time in milliseconds, batch 2, chunk 1 of 3, generation 8. Sequence, batch, and submission IDs restart on UI reload. Frame time is not a wall-clock date; events in one frame can have identical times. `G` changes when queue state invalidates a stage or scheduled preparation. State flags are snapshots **at the event**, so `PAUSE` shows state before the pause is applied, and `SUBMIT_END` shows the submission before its cleanup.

| Event / field | Meaning |
| --- | --- |
| `BATCH_START`, `PREPARE_BEGIN`, `PREPARE_READY`, `STAGED` | A new batch and preparation lifecycle; preparation never sends. `PREPARE_REJECT` explains failed staging without logging the draft. |
| `HOOK_CLOSE_ATTACH`, `HOOK_HISTORY_ATTACH`, `HOOK_SUBMIT_ATTACH` | Hook version changed. `submissionOpen=true` identifies reattachment during an active submission. |
| `SUBMIT_BEGIN` | `id` identifies a submission; `associate` says whether it can belong to the queue. Reasons: `eligible`, `not-hardware`, `gamepad`, `inactive`, `paused`, or `no-stage`. `nested=true` means another submission frame was already open. |
| `HISTORY_CALLBACK` | `associate` passes observed text to queue checks; `unassociated` means eligibility or the stage changed; `ignore` explains an obsolete hook, missing submission, wrong system, or preparation. No text is printed. |
| `SUBMIT_END` | `histories=0` means no eligible history callback was observed in that submission; `associated=0` means none was passed to queued-submission checks. `stageUnchanged=true` while active causes the existing "Submission was not observable" pause. These counters are not proof of delivery. |
| `SUBMIT_BEGIN_IGNORED`, `SUBMIT_END_IGNORED` | A hook could not open/close the tracked submission; includes the hook version and reason. |
| `ENTRY_CLOSE` | Trace-only observer of native `textEntry:Close()`, including stock submission's direct close. `origin` reports `preparing`, `submitting`, or `external`; this observer never pauses or changes ownership. |
| `INPUT_CLOSE` | Observer of `chat:CloseTextEntry()`, used by Escape and focus-loss handling—not every direct entry closure. `ignore-submit` is expected submission-related closure. `ignore-prepare` is preparation-related. `pause` means closure was seen outside either bracket; `submit=-` means no submission frame was open. This alone does not distinguish a user click/Escape from delayed native focus handling. |
| `INPUT_OPEN`, `CHANNEL_CHANGE` | Native reopening and routing activity; target names are omitted. |
| `SUBMISSION_CAPTURED`, `ECHO_CONFIRMED`, `ECHO_IGNORED` | A candidate send, a matching raw outgoing event, or why an event did not confirm it. Unrelated incoming chat can legitimately produce ignored events while a queue is active. |
| `NEXT_SCHEDULED`, `NEXT_TIMER` | Next preparation scheduled for 50 ms later; timer reports `prepare` or `skip` and its original generation. A state change can legitimately invalidate it. |
| `PAUSE`, `ECHO_TIMEOUT`, `RESUME`, `MANUAL_MOVE`, `CANCEL`, `BATCH_COMPLETE` | Reasons for stopping, recovery actions, and confirmed completion. |

Trace state includes `active`, `paused`, `staged`, `pending`, `preparing`, `submit`, and `owned`. Only event metadata, numeric channel IDs, and comparison results are printed—not message bodies, account/character names, whisper targets, or text fingerprints. The existing safety guards remain in place; these traces diagnose the issue rather than fix it.

## Interruption, ambiguity, and recovery

- [ ] Escape, click away/lose focus, or reopen input externally while staged: verify queue pauses and does not overwrite a retained draft. Submit-induced close/focus loss must not wrongly discard a valid submission candidate.
- [ ] Change channel/whisper target by native controls or inline commands. Remaining chunks retain their original destination. Resume explicitly restores that route; automatic next preparation refuses a changed route.
- [ ] Change destination after submitting but before confirmation where reproducible. A retained attempt is matched to its captured route, not the newly selected route; a late match while paused must not auto-prepare another chunk.
- [ ] Zone while staged/waiting: the queue pauses, recording turns off, and neither automatically resumes after loading. A retained in-memory queue needs explicit recovery.
- [ ] Switch to gamepad-preferred mode: preparation is refused. Switch back and explicitly recover; verify no mode-switch send. Gamepad manual-send association is unsupported, not a passing compatibility claim.
- [ ] Where safely reproducible, delay/miss an echo. At ten seconds the queue pauses and Resume refuses a still-pending attempt. A late unique echo may resolve it but must not auto-prepare while paused. Never induce server spam penalties just to create this case.
- [ ] Use identical chunks with identical routes (for example, blank markers and repeated text), or revisit an already-observed chunk. Repeated fingerprints require manual review rather than guessing which event belongs to which send; the fixed four-scalar tag must not be treated as a unique message ID or an ambiguity fix.
- [ ] Manually Next/Cancel an uncertain attempt, then test delayed/duplicate echoes in the controlled harness or client where possible. Old events must not consume a newly ambiguous attempt. Capacity/manual-only fallback should be exercised in mocks, not by sending thousands of live messages.
- [ ] Reload/logout while staged and while pending: no restored armed queue, automatic staging, send, or retry. The unsaved composer/queue is lost. Inspect chat before manually reconstructing anything; reloading is not a deduplication guarantee.
