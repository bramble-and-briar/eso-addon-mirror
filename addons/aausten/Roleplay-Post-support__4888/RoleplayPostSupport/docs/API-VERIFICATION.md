# RoleplayPostSupport API verification and compatibility boundaries

## Baseline and evidence level

The manifest's `## APIVersion` line is the sole API support declaration. Startup uses ESO's manifest-derived `isOutOfDate` flag rather than a hardcoded runtime API list. The source evidence below remains pinned to **101050**; absence of a warning is not evidence of tested compatibility.

This document describes the implemented addon and preserves useful findings from the original source investigation. Research recommendations are distinguished from implemented behavior below. The author has confirmed earlier addon behavior in-game and that ESO preserves zero-width characters through experience with Tongues. This does not establish in-game validation of the v1.2.0 marker protocol; cross-client preservation, editing, and native-limit cases are specified in the [manual checklist](TESTING.md#shared-marker-protocol-across-clients).

## Implemented integration

### Manifest-derived startup compatibility

At startup, the addon obtains the native manager with `GetAddOnManager()` and enumerates indices from 1 through `manager:GetNumAddOns()`. It matches the first return (`name`) of `manager:GetAddOnInfo(index)` against `A.name`, not the display title or a fixed index. The seventh return is the engine's boolean `isOutOfDate`; only a true flag for this addon triggers the once-per-load compatibility warning [E17]. The warning's single `%s` reports the current client API, not a list of supported versions.

This uses ESO's manifest-derived compatibility decision, not raw `APIVersion` metadata: `GetAddOnInfo` does not return that declaration. There is no separate runtime API allowlist to synchronize. For future API releases, test the addon before claiming support, then update the manifest's `## APIVersion` declaration. A false flag or absence of a warning is not proof of in-client compatibility, and does not extend the historical source verification below.

### Localization registry, load order, and boundaries

The [ESOUI localization guide](https://wiki.esoui.com/How_to_add_localization_support) describes loading a default catalog followed by optional `$(language)` overrides, creating addon-prefixed numeric IDs with `ZO_CreateStringId`, registering versions with `SafeAddVersion`, overriding with `SafeAddString` at an equal or newer version, and retrieving text with `GetString`. In the [pinned native implementation](https://github.com/esoui/esoui/blob/f76cf16c4e5be7b234d15dc7f676febffa64c5bb/esoui/ingamelocalization/localizegeneratedstrings.lua#L8-L22), `SafeAddVersion` sets the required baseline; `SafeAddString` compares against that baseline and replaces only the text, without advancing the registered version. This localization reference is separate from the pinned chat/API research below.

The implemented manifest loads `RoleplayPostSupport.lua` first to establish the namespace and defer lifecycle work, then `lang/default.lua`, optional `lang/$(language).lua`, and `RoleplayPostSupport_Localization.lua`. The remaining five root modules retain their order: Splitter, Sessions, Queue, Chat, UI. The English catalog creates **166 `RPS_` IDs**, each at version **1**; it does not use ESO's `SI_` namespace. English is the default, without a duplicate `en.lua`; German, Spanish, and French overrides are supplied in `lang/de.lua`, `lang/es.lua`, and `lang/fr.lua`. Each locale uses a keyed table covering the same 166 keys and registers version-1 overrides with `SafeAddString(_G["RPS_" .. key], value, 1)`. ESO permits an absent selected locale file; a partial override leaves unmodified English entries registered. Future two-letter locales use `SafeAddString` on existing IDs, not another `ZO_CreateStringId` call.

`A.L(key, ...)` resolves `_G["RPS_" .. key]`, asserts that the ID exists, and calls `GetString` on every lookup. With arguments it applies Lua `string.format`; without arguments it returns the catalog text unchanged. Fallback comes from the registered default catalog, not a second English table in the helper. Complete display templates are available for translation. Preserve `%s`/`%d` count, type, and order, `%%` for literal percent signs in formatted entries, Lua backslash/newline escapes, and ESO color markup. These templates do not use `<<1>>` or `zo_strformat`; existing name-specific ESO grammar formatting is separate. `UI_RECORD_WARNING_OFF` and `UI_RECORD_WARNING_ON` are simple status strings with no format arguments; the active status retains red ESO color markup. `UI_RECORD_WARNING_OFF` reminds users to obtain permission before recording. Unsaved participant edits use `UI_PARTICIPANTS_DIRTY` to add a save reminder, with a separate `UI_PARTICIPANTS_SAVED` confirmation after saving.

Localization covers UI labels, notices, validation errors, and human-readable queue reasons, not user messages, names, continuation markers, or the shared wire tag. `/rps` subcommands and machine trace event/reason codes remain stable. Sessions still returns its existing `snake_case` errors; only the UI maps them to readable localized messages. Runtime state, queue matching, persistence schema, and v1.2.0 marker compatibility are unchanged; no SavedVariables migration or version bump is introduced.

Offline coverage uses `tests/localization_fixture.lua` to mock `ZO_CreateStringId`, `SafeAddVersion`, `SafeAddString`, and `GetString` while loading the real catalog/helper. `tests/localization_spec.lua` checks all 166 keys, references, fallback, override versions, typed formatting, and raw-data preservation. The splitter now depends on this localization surface even though it has no chat/UI dependency. These fixtures model the API contract, not the ESO loader or rendered UI; locale switching and layout checks are in the [manual checklist](TESTING.md#localization-and-locale-fallback).

### Prepare, never submit

[RoleplayPostSupport_Chat.lua](../RoleplayPostSupport_Chat.lua) populates native input exclusively through **`StartChatInput(text, channel, target)`**. The pinned wrapper has precisely that argument order, delegates to the active chat system, and returns no success flag [E1]. The underlying start can silently refuse when the UI is hidden, game unfocused, player inactive, a blocking scene is open, or communication checks fail [E2].

Before calling it, the adapter validates the selected destination and refuses to overwrite unrelated or edited nonempty input. `Chat.Prepare` strips one exact leading message tag for its empty-body and leading-slash-command checks, so that tag cannot hide either condition. Length validation, ownership, readback, submission capture, and echo matching retain the exact raw wire text, including any tag. After calling it, the adapter requires the same active chat-system object, an open entry, exact text equality, and the expected channel/normalized whisper target. This readback is essential: a function return alone is not evidence of successful staging. It is not a separate focus guarantee or server acknowledgement.

The addon does not invoke `SendChatMessage`, `SubmitTextEntry`, `ZO_ChatSystem_SubmitChat`, `AutoSendTextEntry`, or `AutoSendChatInput`, and does not synthesize input. Hooks on submission methods are observers, not invocations. A timer may prepare another chunk; it cannot send it.

### Runtime length, not a claimed server cap

The pinned XML sets `maxInputCharacters="MAX_TEXT_CHAT_INPUT_CHARACTERS"` [E3]. **The numeric native/server message limit is not verified from these sources.** Neither pChat's shortcut constants nor the composer's editor cap establish that limit.

`Chat.GetLimit()` reads the runtime global and active edit control's `GetMaxInputChars()`. It falls back to the control limit if the global is absent/nonpositive, takes the smaller positive value when both are usable, and requires a positive integer. Without a valid result, preparation is disabled. The user's applied maximum cannot exceed it; preview also clamps against the current runtime result.

`A.Preview` removes one exact leading tag from copied input before splitting, then returns readable chunks with a budget of `min(applied max, runtime limit) - 4`. Normal prefix/suffix continuation reservations apply within that reduced budget. `A.Start` prefixes **every** resulting chunk, including a single chunk, regardless of recording state or the session filter. The minimum effective maximum is **5** with empty continuation markers (four tag scalars plus one body scalar); default continuations need additional room.

The splitter's budget counts validated **Unicode scalar values**, including continuation markers. It does not count bytes or grapheme clusters. Exact staging readback detects text alteration/truncation by the native control, but does not prove that scalar counting matches all engine/server constraints. Combining sequences, supplementary-plane characters, and native/server acceptance remain runtime checklist items.

### Shared v1.2.0 wire convention

`Splitter.MESSAGE_TAG` is exactly four U+200B ZERO WIDTH SPACE characters (`string.rep("\226\128\139", 4)` in Lua): **12 UTF-8 bytes and 4 Unicode scalars**, not NUL bytes. `Splitter.MESSAGE_TAG_LENGTH` is 4. `Splitter.StripMessageTag` recognizes only that exact prefix at the start, removes it once, and returns the body and a boolean classification. It does not strip arbitrary, embedded, or repeated tags recursively.

The prefix is a shared classification convention, **not authenticated provenance**, a per-post token, or transmitted queue metadata. Removing it excludes a message from addon-only capture; copied text and other addons may mimic it. Older RPS releases do not tag outgoing chunks. Participants need RPS **1.2.0+ or the identical convention** for addon-only capture. Exact marker survival through client/server transport and native edits is a protocol-specific runtime check, distinct from the author's Tongues experience.

### Manual submission observation

The stock keyboard Enter handler can select autocomplete rather than submit. When submission does occur, the pinned stock `SubmitTextEntry` first copies text, closes/clears the entry, calls `AddCommandHistory(text)`, parses commands, and finally validates the route before its private send call [E4, E5]. Therefore neither Enter, history capture, focus loss, nor an empty box alone proves a message was sent.

`Chat.EnsureHooks()` attaches lazily to `ZO_GetChatSystem()` when preparing and rejects gamepad-preferred mode. It checks for the required history/submit methods and installs:

- An observational **`ZO_PreHook` on `SubmitTextEntry`** opens a local submission bracket. Queue association is eligible only for an active, unpaused, staged queue in keyboard mode while `WINDOW_MANAGER:IsHandlingHardwareEvent()` is true. Other observed submissions are tracked only to detect ambiguity. Its callback returns no truthy value, so it does not suppress stock submission.
- **`SecurePostHook` on the final `AddCommandHistory` method**. Inside that bracket it captures the incoming `text` argument and current route. It does not read the now-cleared input or decorated stored history.
- **`SecurePostHook` on `SubmitTextEntry`** to close the bracket; if the original stage is still outstanding, the queue pauses rather than assuming success. Cleanup is bound to that original stage/ownership, so a command such as `/rps next` can prepare a replacement without the old submission invalidating it.
- **`SecurePostHook` on `StartTextEntry`, `CloseTextEntry`, and `SetChannel`** to invalidate ownership/pause for external reopen/close or destination changes. Close during observed submission is exempted so stock submit-induced focus loss does not discard the candidate.

A temporary diagnostic **`SecurePostHook` on `textEntry:Close()`** also observes stock submission's direct entry-close path ([sharedchatsystem.lua:215–226](https://github.com/esoui/esoui/blob/f76cf16c4e5be7b234d15dc7f676febffa64c5bb/esoui/ingame/chatsystem/sharedchatsystem.lua#L215-L226)). It only emits opt-in `ENTRY_CLOSE` traces; it never pauses, clears ownership, or submits. `/rps debug` enables numbered local traces using [`GetFrameTimeMilliseconds()`](https://github.com/esoui/esoui/blob/f76cf16c4e5be7b234d15dc7f676febffa64c5bb/ESOUIDocumentation.txt#L11853-L11854), with timestamp fallback, and direct `d()` output rather than UI notifications. Trace logging is guarded so logger failures cannot abort native submission. See [trace interpretation and reproduction](TESTING.md#temporary-chat-tracking-traces).

History/submit/diagnostic-close method identities are rechecked at later preparation, with version guards to disable old observer callbacks. This is not continuous detection of every third-party replacement during an already-staged attempt.

`ZO_PreHook` is an ESO-provided Lua wrapper that assigns a replacement function [E6]. This implementation does **not** claim literal zero monkey-patching. It does not install a custom send implementation, replace router formatters, hook private `SendChatMessage`, or use the research alternative of a named `OnEnter` observer described below. Hardware-event gating narrows association but cannot prove that another addon never invoked a submission function during a hardware event [E7]. The enforceable invariant is that **RoleplayPostSupport itself never initiates submission**.

### Raw events and conservative confirmation

The independent event callback receives:

```text
(eventCode, channelType, fromName, text, isCustomerService, fromDisplayName)
```

The engine payload has no message ID, submission token, explicit outgoing flag, or separate target argument [E8]. The adapter sends the raw event to the queue first and then to the optional archive with any confirmed queue metadata. It does not parse chat-window output or depend on `FormattedChatMessage`.

For queue confirmation on ordinary player channels, a pending attempt requires exact raw text and channel plus local sender identity. A supplied account identity must match `GetDisplayName()`; only when it is absent does matching fall back to the local character/account name. Customer-service events are excluded.

Whispers are staged on `CHAT_CHANNEL_WHISPER`, but outgoing echoes use **`CHAT_CHANNEL_WHISPER_SENT`**. On that outgoing event, `fromName`/`fromDisplayName` describe the **recipient** as consumed by stock and pChat formatters [E9, P4]. The implementation therefore matches the captured recipient against those normalized fields, not against the local sender's account. It does not guess character/account aliases.

Only one queued attempt can be pending. Its actual captured text, route, index, and post ID remain fixed while waiting. A match advances once and, if not paused, schedules the next **preparation** after 50 ms. If the match arrives while paused, explicit Resume is required to prepare the next chunk. A 10-second timeout pauses but retains the pending attempt; it does not declare failure or retry.

The queue tracks distinct confirmed chunk indexes per batch. When the final chunk is confirmed and all indexes have been observed, it notifies the UI with that batch's post ID. The UI clears Compose and its preview only if the draft belongs to that batch and has not been edited since Start. Manual navigation is not confirmation, and clearing the composer does not alter session records or retired fingerprints. The last chunk's echo alone is insufficient if an earlier chunk remains unconfirmed.

Confirmed, abandoned, or cancelled pending attempts, plus non-command submissions observed outside queue association (including paused sends), are retired by exact text/channel/normalized-target fingerprint. Reusing a retired fingerprint makes a new attempt ambiguous and requires manual recovery. The fixed shared tag does not distinguish repeated text or solve this ambiguity. Fingerprints are held in memory without expiry until UI reload/logout, bounded at 4,096 entries; exceeding capacity switches later association to manual-only handling. This sacrifices automatic progression for repeated legitimate messages rather than attributing a delayed old echo to new text. An observed unassociated submission matching a pending fingerprint also makes that pending attempt ambiguous. Observation begins only after the first hook attachment and cannot cover every other addon's send path. It cannot establish exactly-once delivery, resolve unobserved identical own sends, or prove a recipient received/read anything.

### Session capture is not queue route matching

The optional archive uses the existing source-verified player channel set: Say, Emote, Yell, Group, Zone, Guild/Officer slots, language channels, and both `CHAT_CHANNEL_WHISPER` and `CHAT_CHANNEL_WHISPER_SENT`. This is a capture allowlist, not an expansion of the composer's send destinations. System/monster channels and customer-service events are excluded. On eligible channels, own outgoing events pass the sender filter even with an empty participant list; other senders must match a saved participant. Thus outgoing whispers **to anyone** are eligible, while incoming whispers require a named participant. Neither direction is filtered by a stored session target.

The per-session boolean `addonOnly` defaults to `false` on every new session; a missing legacy flag is OFF. **Record addon-marked only: ON** requires the exact leading tag for every otherwise eligible sender, including own outgoing messages and participant whispers. Tagged outgoing whispers to anyone remain eligible even with ON; unmarked outgoing whispers are excluded. Incoming whispers still require a participant, and no marker bypasses sender, channel, or customer-service exclusions. OFF allows both marked and unmarked eligible messages.

`Sessions.SetAddonOnly` requires a boolean and updates the selected session's saved flag without stopping recording. A live toggle affects only future capture, not existing archives. No SavedVariables version bump or migration is required; legacy records are not rewritten or backfilled.

Session creation retains Compose's route as metadata, not capture scope. `Sessions.SetRecording` does not validate the legacy stored route as a send destination. Existing RoleplayPostSupport sessions use the same all-channel behavior without migration when explicitly armed; old records are not rewritten, and recording is never automatically resumed. This is separate from the absence of an import from the older LongRPPost SavedVariables table.

Every newly recorded message strips one exact leading tag from stored `text` and stores boolean `addonMarked`, even with addon-only OFF. Unmarked text is unchanged. Classification happens independently of queue correlation, after ordinary capture eligibility checks; raw text is still passed to the queue before archive processing. Each new record stores the actual event channel. Its target is `nil` for non-whispers; for either whisper direction it is the actual event correspondent, preferring formatted `fromDisplayName` and falling back to formatted `fromName`. An outgoing whisper record still stores the local player as sender, rather than mistaking the recipient fields for sender identity [E9, P4].

**Queue checks are unchanged.** Recording an event on another channel or involving another whisper correspondent does not acknowledge a pending attempt or alter its route. Only an unambiguous local outgoing queue match supplies `postId`/`index`/`count` metadata. A remote tag or an unassociated marked manual message supplies none. The wider capture scope is a privacy expansion: the Sessions UI must disclose all player chat including whispers, and users must explicitly start recording with that scope in mind. Addon-only filtering is not authentication or a consent/privacy boundary; it still permits tagged outgoing whispers to anyone. See the [privacy guidance](../README.md#privacy-persistence-and-retention) and [session checklist](TESTING.md#sessions-consent-and-retention).

### Route changes, modes, and lifecycle

The implementation reads the active system rather than assuming a permanent `CHAT_SYSTEM` object [E10]. Its observed route changes pause the queue without retargeting remaining chunks. A pending attempt keeps its old route; a late old-route echo can still resolve that attempt. Resume explicitly requests the original route. Preparation in gamepad-preferred mode is refused; there is no independently validated gamepad send association.

The main window's `OnShow` enables cursor mode through the public [`SetGameCameraUIMode(true)` API](https://github.com/esoui/esoui/blob/f76cf16c4e5be7b234d15dc7f676febffa64c5bb/ESOUIDocumentation.txt#L11633). This covers `/rps` and both indicator Open buttons without taking editor focus, forcing cursor mode during refreshes, or disabling it on close. ESO's [scene manager also uses this API to enter UI mode](https://github.com/esoui/esoui/blob/f76cf16c4e5be7b234d15dc7f676febffa64c5bb/esoui/ingame/scenes/ingamescenemanager.lua#L66-L74).

Stock Escape clears native keyboard input, while some cancel/focus-lost paths preserve it [E11]. Queue Cancel itself does neither: it leaves native input untouched. A different native draft blocks preparation.

[RoleplayPostSupport.lua](../RoleplayPostSupport.lua) constructs account-wide/world-namespaced `RoleplayPostSupportSavedVariables` and initializes Sessions during its matching **`EVENT_ADD_ON_LOADED`**, not during player activation. First `EVENT_PLAYER_ACTIVATED` initializes chat destinations, settings validation, UI, and event subscriptions. Player deactivation pauses any queue and turns recording off. The pinned [SavedVars implementation explicitly requires construction in the addon-loaded event](https://github.com/esoui/esoui/blob/f76cf16c4e5be7b234d15dc7f676febffa64c5bb/esoui/libraries/utility/zo_savedvars.lua). Drafts, queue state, fingerprints, selected session, and recording state are not saved or restored.

## pChat integration

The pinned pChat source makes several integration choices important [P1–P6]:

| pChat behavior | Implemented response |
| --- | --- |
| Replaces `AddCommandHistory`, optionally adding route prefixes to stored history | Lazily observe the final outer method's incoming argument, not the stored record. |
| Expands `!name` shortcuts in a prehook before stock reads text | Capture history-call text after expansion. The current code treats changed text as an edit when route and echo match; it does **not** add a special macro-expansion approval step. Preview is not a promise of final text with macros enabled. |
| Calls `AddCommandHistory` during history restoration | Ignore history calls outside a native submission bracket; only staged/hardware submissions qualify for queue association. No restored-history import or queue restoration is implemented. |
| Changes channel/target when switching chat tabs | Observe `SetChannel`, preserve the original queue destination, and refuse automatic staging into a changed route. |
| Replaces the chat router formatter; filtering may suppress displayed output or omit stock return values | Subscribe separately to raw `EVENT_CHAT_MESSAGE_CHANNEL`. Visible formatted output is not the acknowledgement source; archives can include eligible raw events even when pChat hides them. |

The manifest has no pChat dependency or optional dependency declaration; lazy attachment, not declared ordering, is the implemented strategy. A future pChat version, another chat addon, or a late method replacement can invalidate assumptions.

## History ordering and date display

History defaults to insertion order (oldest to newest). The Sessions **Oldest first / Newest first** toggle saves a shared account/world display preference in `historyNewestFirst`; only literal `true` selects newest-first, so missing legacy values use oldest-first without an archive migration or schema bump. Both modes traverse the stored sequence without sorting or mutating it, preserving insertion order for equal-second timestamps. Oldest-first page 1 holds the oldest ten retained entries; newest-first page 1 holds the latest ten in reverse order. Selecting a session, changing display order, or observing a newly appended record follows the latest entry: last page/bottom for oldest-first, page 1/top for newest-first, even when retention eviction keeps the count constant. The bottom position uses `GetScrollExtents() + 1`, matching the native multiline editor's [wheel-scroll bounds](https://github.com/esoui/esoui/blob/f76cf16c4e5be7b234d15dc7f676febffa64c5bb/esoui/libraries/zo_templates/editboxtemplates_keyboard.xml), so wrapped lines are included without moving focus. Manual page changes start at the top; unrelated refreshes preserve browsing and scrolling.

Saved `GetTimeStamp()` values are displayed with guarded `os.date("%Y-%m-%d %H:%M:%S", timestamp)`, following pChat's historical-time use of `os.date("%c", timeStamp)` in [CopyHandler.lua:1054–1060](https://github.com/Baertram/pChat/blob/3a433e33fe8fcffbe24497374e4f98d75217eaef/pChat/CopyHandler.lua#L1054-L1060). pChat stores the [GetTimeStamp value](https://github.com/Baertram/pChat/blob/3a433e33fe8fcffbe24497374e4f98d75217eaef/pChat/MessageFormatters.lua#L1138-L1141) as [rawTimestamp](https://github.com/Baertram/pChat/blob/3a433e33fe8fcffbe24497374e4f98d75217eaef/pChat/ChatHistory.lua#L436-L437). [Lua 5.1 `os.date`](https://www.lua.org/manual/5.1/manual.html#pdf-os.date) uses the supplied historical time and host local timezone unless the format begins with `!`; this implementation uses local time. It does not combine a date with the current `GetTimeString()` or infer old offsets from today's clock. Invalid timestamps, missing `os.date`, or formatting failures display `Unknown time` and do not modify the archive.

## Additional retained research findings

These source-level constraints and alternatives inform maintenance; they are **not** claims that additional observers or policies are implemented.

- **Staging arguments:** a nonempty `StartChatInput` text replaces the input; nil/empty text does not clear it. Pass the channel explicitly when selecting a destination: a target alone does not reliably retarget the active channel. The underlying `StartTextEntry` has a fourth `dontShowHUDWindow` parameter, but the global wrapper does not forward one [E1, E2].
- **Observation alternatives:** the native API documents named additional `SetHandler` callbacks with BEFORE/AFTER ordering, permitting a proposed non-replacing keyboard `OnEnter` bracket. Ordering against stock/autocomplete handlers and inherited-method secure hooks still requires in-client validation. No `SecurePreHook` was documented in the inspected VM list; private `SendChatMessage` is not a supported dependency for this design [E7, E12]. `ZO_PreHook`/`ZO_PostHook` and their handler variants replace functions or handlers, unlike that proposed named observer [E6].
- **Route notifications:** `OnChatChannelUpdated` has no payload. `CHAT_ROUTER:GetCurrentChannelData()` returns `(channelData, target)` after the router updates them; do not assume keyboard/gamepad cached fields are already updated by another callback. Inline channel parsing and Tab target cycling can change the route independently of draft text. Do not call `TextToSwitchData` or `ValidateChatChannel` just to classify a candidate: they have side effects [E13, E14].
- **Gamepad scope:** the stock user-pressed gamepad Send action internally calls `AutoSendChatInput` through a separate edit control. That stock action is not inherently an autonomous send, but a keyboard-only observer cannot establish its association. This addon deliberately refuses gamepad-preferred preparation rather than claiming that path is supported [E15].
- **Uncertainty:** retain immutable attempted text/route separately from the editable draft, account for an echo that may arrive before a submit posthook finishes, and never treat timeout as safe-to-retry proof. Identical delayed echoes cannot establish exactly-once delivery without engine message IDs. The original research recommended explicit preparation after each confirmation and special review of macro expansion; the implemented behavior instead allows automatic **preparation**, never sending, and treats expansion as edited text as documented above. Draft/queue restoration was a research option, not an implemented persistence feature.
