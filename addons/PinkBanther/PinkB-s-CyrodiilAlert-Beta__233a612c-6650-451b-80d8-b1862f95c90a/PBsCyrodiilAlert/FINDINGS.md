# シロディールの拠点が攻撃されているかを、どうやって知るか — 調査結果

調査対象: `esoui/esoui`（live ブランチ、ゲームクライアント本体の Lua ソース + `ESOUIDocumentation.txt`）

## 結論

**マップが使っているのと同じ5つの公開関数を読むだけで足りる。** どれも「クライアントが既に持っている
値の読み取り」であり、サーバー通信も、ゲーム側状態の書き換えも一切発生しない。

```lua
GetNumKeeps()                          -- 拠点の総数
GetKeepKeysByIndex(index)              -- -> keepId, bgContext
GetKeepType(keepId)                    -- -> KEEPTYPE_*
GetKeepAlliance(keepId, bgContext)     -- -> ALLIANCE_*  所有陣営
GetKeepUnderAttack(keepId, bgContext)  -- -> bool        交差した剣のピン
```

`ESOUIDocumentation.txt` の該当行（16084/16087/16108/16111/16160/16187 行目付近）にすべて記載があり、
`private` / `protected` のマーカーは付いていない。ただしこのドキュメントのマーカーは当てにならない（過去に無印の `SetSetting` が private だった）ので、
**実際にクライアント自身が同じ関数を呼んでいるか**を確認した:

- `esoui/ingame/map/worldmap.lua:1824` `RefreshKeeps()` — `GetNumKeeps()` → `GetKeepKeysByIndex(i)` → `AddKeep(keepId, bgContext)`
- `esoui/ingame/map/cmaphandlers.lua:153` `CMapHandlers:RefreshKeeps()` — 同じ流れに `IsLocalBattlegroundContext(bgContext)` のふるい付き

つまりこのアドオンがやっているのは、マップが毎回描き直すときにやっていることと同じ読み取りである。

## bgContext（キャンペーンの二重報告）

`GetKeepKeysByIndex` は**同じ拠点を2回返す**。いま立っているキャンペーン（`BGQUERY_LOCAL`）と、
ホームに設定しているキャンペーン（`BGQUERY_ASSIGNED_CAMPAIGN`）の2行である。

クライアント側の判定関数がそのまま使える:

```lua
-- cmaphandlers.lua:158
if IsLocalBattlegroundContext(bgContext) then
    self:AddKeep(keepId, bgContext)
end
```

これを入れないと、

- 通知が全部2重に出る
- **いま自分がいないキャンペーンの攻城戦を通知してしまう**

の2つが同時に起きる。テスト（`test/harness.lua`）の拠点テーブルは、この2行構造をわざと再現している。

## 拠点の種類

`KeepType` 列挙は10種類（`ESOUIDocumentation.txt:2121`）。

| 種類 | 監視対象 | 理由 |
| --- | --- | --- |
| `KEEPTYPE_KEEP` / `OUTPOST` / `ARTIFACT_KEEP` / `BORDER_KEEP` | ○（初期オン） | 得点対象の拠点 |
| `KEEPTYPE_TOWN` | ○（初期オン） | 村 |
| `KEEPTYPE_RESOURCE` | △（初期オフ） | 農場・鉱山・製材所。ソロで頻繁に取り合いになり、オンにすると通知で埋まる |
| `KEEPTYPE_IMPERIAL_CITY_DISTRICT` | △（初期オフ） | 帝都の地区。入れ替わりが激しすぎる |
| `KEEPTYPE_BRIDGE` / `MILEGATE` / `ARTIFACT_GATE` | ×（常に対象外） | 所有できる拠点ではなく構造物。「奪われた」が定義できない |

`KEEPTYPE_*` は**テーブルコンストラクタで一気に書かず、1つずつ登録**している。定義されていない定数が
1つでもあるとコンストラクタが nil キーでロード時に落ち、アドオンごと読み込まれなくなるため。
1つずつなら、知らない種類は「監視しない」で済む。

なお、拠点の種類を表示するための**クライアント側の文字列は存在しない**（`SI_KEEPTYPE*` は無い）。
「砦」「村」などのラベルは本アドオンの `lang/` で持っている。

## タイマーか、イベントか

`EVENT_KEEP_UNDER_ATTACK_CHANGED (keepId, bgContext, underAttack)` は実在する
（`ESOUIDocumentation.txt:27516`）。それでもタイマーにしたのは、要望がそうだったからだけではない:

1. **監視周期が設定値になる。** 通知の粒度をサーバー任せにしない。
2. **エッジを取りこぼさない。** ゾーン移動中にイベントが落ちても、次の走査が現実を読んで自力で直る。
3. **「1分後もまだ攻撃されているか」は現在の状態への問い**であって、エッジへの問いではない。
   最初の通知をイベントで受けたとしても、この再通知は結局タイマーが要る。

コストは走査1回あたり数十個の値の読み取りだけで、測る価値がない。失うのは周期未満の遅延
（初期値5秒なら最大5秒）。

## 「自陣営が攻撃を開始した」は判定できるか

**できない。** キープAPIに「攻撃している陣営」を返すものは1つも無い。`GetKeepUnderAttack` は
真偽値だけで、3陣営のキャンペーンでは、敵拠点での戦闘が自陣営の攻撃なのか、残り2陣営同士の
衝突なのかを区別する材料がここには無い。

唯一関係するのが、クライアント自身がキープのツールチップで使っている攻城兵器の数である:

```lua
-- keeptooltip.lua:158-173
if DoesKeepTypeHaveSiegeLimit(keepType) then
    local numPlayerSiegeWeapons = GetNumSieges(keepId, battlegroundContext, playerAlliance)
    ...
    for i = 1, NUM_ALLIANCES do  -- 他陣営の分は 0 でなければ表示
```

自陣営が所有していない拠点に自陣営の攻城兵器が立っているなら、それは自陣営の攻めである。
ただし**証拠であって証明ではない**（攻城兵器を使わない攻撃はいくらでもある）ので、本アドオンは
これを「自陣営が攻撃中」と言い換えず、**基数をそのまま併記する**にとどめている。

```
[砦] アリウス砦（アルドメリ・ドミニオン）で戦闘が始まりました。自陣営の攻城兵器 2基
```

`DoesKeepTypeHaveSiegeLimit` のふるいはツールチップと同じものを入れてある。資源には攻城制限が
無く、数字に意味が無いため。

したがって緑の通知の文面は「**戦闘が始まりました**」であって「自陣営が攻撃を開始しました」ではない。
分かっていないことを断定しない、という一点で決めている。

### 「自陣営の攻撃だけ」に絞る（初期オン）

その攻城兵器の数を条件そのものに使うのが `offenseOursOnly`。自陣営が所有していない拠点に
自陣営の攻城兵器が立っているときだけ緑を出す。**近似であって判定ではない**ので、外し方は3つある。

- 攻城兵器を使わない攻撃は永久に出ない
- 攻城兵器を置く前＝攻撃開始直後は出ない（設置後に出る）
- `DoesKeepTypeHaveSiegeLimit` が false の拠点（資源・村・地区）は条件を満たしようがなく、
  オンの間まったく通知されない

実装上は**通知の抑制であって監視の中止ではない**。エントリは作るので、

- その拠点が自陣営のものになれば「占領しました」は出る
- 後から自陣営の攻城兵器が立てば、その時点で「開始」として出る（再通知としてではない。
  こちらにとってはそこが開始だから）

この近似が成立するかどうかは攻城兵器の数が遠くの拠点でも届いているかに完全に依存する。
`/pbalert list` で常に空欄なら、この設定はその環境では機能しないのでオフにするしかない。

## 巻物とヴォレルドルング — 「誰が持っているか」が取れるのはどちらか

**取れるのは巻物だけ。** AvA関連のイベントでプレイヤー名を渡してくるものは2つしかなく、
うちシロディールで使えるのは1つである。

| イベント | 名前 | 対象 |
| --- | --- | --- |
| `EVENT_ARTIFACT_CONTROL_STATE` | **あり**（`characterName`, `displayName`） | エルダースクロール |
| `EVENT_MURDERBALL_STATE_CHANGED` | あり | バトルグラウンドのボール |
| `EVENT_DAEDRIC_ARTIFACT_OBJECTIVE_STATE_CHANGED` | **なし**（`holderAlliance` のみ） | ヴォレルドルング |

ヴォレルドルングは、クライアント自身のアナウンスも「<<1>>が明らかになった。」
「<<1>>は使い手を探している。」だけで、所持者どころか陣営名すら出していない
（`centerscreenannouncehandlers.lua:619`）。ポーリング側（`GetObjectiveInfo` /
`GetObjectiveControlState` / `GetObjectivePinInfo`）にも名前は無い。

そこで:

- **巻物** → `EVENT_ARTIFACT_CONTROL_STATE` を購読し、名前つきで通知する。
  文面はクライアントの `ARTIFACT_EVENT_DESCRIPTIONS`（同ファイル12行目）と同じ4種類＋
  タイマー返還に対応させた。`keepId == 0` が「拠点から奪った」ではなく「地面から拾った」の
  合図になっている点もそのまま踏襲している。名前は `IsInGamepadPreferredMode()` で
  表示名／キャラクター名を切り替える（クライアントと同じ判断）。対応表に無いコントロール
  イベントは黙って捨てる。文面を推測して増やすと、対処のしようがない行でチャットが埋まるため。
- **ヴォレルドルング** → 戦況表示に陣営だけ出す。陣営はマップピンの種類
  （`MAP_PIN_TYPE_AVA_DAEDRIC_ARTIFACT_VOLENDRUNG_<陣営>` と `_NEUTRAL`）から読む。
  クライアント自身がそこに持たせているため。`IsCarryableObjectiveCarriedByLocalPlayer` で
  「自分が持っている」だけは判定できるので、その場合だけ別の行にしている。
  出現していない（`OBJECTIVE_CONTROL_STATE_UNKNOWN`）ものは行を出さない。

**未検証:** どちらのイベント／状態も、キャンペーン全体に配信されるのか、近くにいる必要があるのかは
ドキュメントからは読み取れなかった。実機での確認が要る。

## ヴォレルドルングの時間

**出現・公開・消滅の時刻を返すAPIは無い。** ゲーム本体のアナウンス（「使い手を探している」
「明らかになった」「オブリビオンに戻った」）にも時間は入っていない。出現時刻も公式には
公開されていない。

そこで3つのアナウンスを受けた時刻をアドオン自身で記録し、経過時間を出す。

| アナウンス | イベント |
| --- | --- |
| 使い手を探している | `EVENT_DAEDRIC_ARTIFACT_OBJECTIVE_SPAWNED_BUT_NOT_REVEALED` |
| 明らかになった | `EVENT_DAEDRIC_ARTIFACT_OBJECTIVE_STATE_CHANGED`（UNKNOWN → 非UNKNOWN） |
| オブリビオンに戻った | 同上（非UNKNOWN → UNKNOWN） |

判定はクライアント自身のアナウンス処理（`centerscreenannouncehandlers.lua:619`）と同じ遷移。

予測はコミュニティの観察値（UESP、2026年5月時点。**ZOSの公式値ではない**）を使う。

- 出現から10〜15分で公開
- 公開から約30分で消滅（持ち主が4〜5回替わるとそれより早い）
- 1キャンペーンで1日4〜5回、時刻は不定 → **次の出現は予測しない**

予測は必ず「目安」と表示し、過ぎたら負数ではなく「まもなく」にする。
時計は見ていたものしか知らないので、入場前から出ていた場合は「経過不明」。
別キャンペーンの時計は表示しない（記録時のキャンペーンIDと照合）。

自分が所持している間だけは `GetUnitPower("player", COMBAT_MECHANIC_FLAGS_DAEDRIC)`
（`huddaedricenergymeter.lua:312`、HUDの飢餓メーターの中身）で残量を出せる。
クライアントが渡してくれる寿命の数字はこれだけ。

**未検証:** 3つのイベントが遠方でも届くか（キャンペーン全体に配信されるか）。

## 全体マップ — ワールドマップを借りない

PB's MiniMap（と元になった Votan's Minimap）は、ゲームのワールドマップ（`ZO_WorldMap`）を
HUDに置いてミニマップにしている。**ワールドマップは1枚のコントロールで、1つの地図を1つの
縮尺でしか出せない**。同じ方式で2つ目のアドオンが借りると、1つ目から取り上げることになる。
そこでこのアドオンは、同じ部品から自前の地図を組み立て、`ZO_WorldMap` にもシーンにも触らない。

地図IDを指定して取れるので、ワールドマップが表示している地図を切り替える必要がない。

```lua
local mapId = GetMapIdByIndex(GetCyrodiilMapIndex())
GetMapNumTilesForMapId(mapId)          -- タイル数（横×縦）
GetMapTileTextureForMapId(mapId, i)    -- タイル画像。行優先（worldmaptiles_manager.lua:29 と同じ並べ方）
GetUniversallyNormalizedMapInfo(mapId) -- 共通座標空間での地図の位置と大きさ
```

**ピン座標は「現在の地図」基準で返ってくる。** `GetKeepPinInfo` も `GetMapPlayerPosition` も、
ワールドマップが今セットしている地図（シロディール、その中の都市、ミニマップがズームした先…）の
正規化座標を返す。現在の地図とシロディールの両方の共通座標空間上の位置を使って変換する。

- 砦は動かないので、一度求めた位置を保持し、所有者と攻撃状態だけ読み直す
- 変換できない（現在の地図の共通座標が無い）ときは、砦は最後の正しい位置のまま、
  プレイヤーの矢印は推測せず隠す
- プレイヤーの向きは `GetPlayerCameraHeading()`（クライアントのピン更新と同じ、
  `mappin_manager.lua:792`）

ピンの絵はゲームのピン表 `ZO_MapPin.PIN_DATA[pinType].texture` を**読むだけ**。値が文字列の
場合だけ使い、関数が入っているものは呼ばない（クライアントのコードを呼ばない方針）。その場合は
別の絵で代用せずアイコンを出さない。攻撃マークは `MAP_PIN_TYPE_KEEP_ATTACKED_LARGE` の絵を、
ワールドマップと同じく砦の下に描く。

表示はシロディールのみ（帝都は別の地図）。**メニュー表示中は隠す**が、その判定は
`SCENE_MANAGER:GetCurrentScene()` を読むだけで、フラグメントの追加などシーンへの操作はしない。
プレイヤーの矢印を動かす200msのタイマーは、地図が表示可能な間（オン・シロディール内）だけ動く。

**未検証（実機）:** 変換後のピンが実際の砦の上に乗るか。ずれていた場合に原因を1回で特定できるよう、
`/pbalert map probe` で地図ID・共通座標・プレイヤー位置（現在の地図基準とシロディール基準）を出す。

### 目標のピンは「有効」かつ「見える」ものだけ（2.5.3）

実機で、全体マップにヴォレルドルングが大量に描かれた。**ヴォレルドルングが出現しうる地点は
それぞれが独立した目標（objective）で、シロディールに23か所ある。** どれも `GetObjectivePinInfo` に
正しいピン種別（中立のヴォレルドルング）と座標を返す。実際に出ているのは多くても1つ。

ゲーム本体の地図は、現在位置ピンを置く前に3つ確かめている（`mappin_manager.lua:677-706`）。

1. `IsObjectiveEnabled` — その目標が使われている（出現地点として有効）
2. `IsObjectiveObjectVisible` — 物がそこに見えている
3. ピン種別が `MAP_PIN_TYPE_INVALID` でない

初版はこの3つを省いていたため、23か所すべてを描いていた。同じ3つを同じ順に入れた。戦況表示の
ヴォレルドルング行も `IsObjectiveEnabled` を確かめるようにした（状態が UNKNOWN 以外かだけでは、
有効でない地点を拾いうるため）。

テストは実機と同じ形を再現する：無効な出現地点23か所＋有効な1か所。修正前のコードでは
ちょうど23本描かれ、スクリーンショットと一致することを確認した。

### トランシスタスの経路

ワールドマップは `GetKeepTravelNetworkLinkInfo(linkIndex, bgContext)` で各経路の種別・所有陣営・
両端の座標を受け取り、Line コントロール（`ZO_MapKeepLink`、`worldmap.xml:19`）で描いている
（`worldmap.lua:520-580`）。座標は他のピンと同じく「現在の地図」基準なので、同じ変換でシロディール
基準にする。両端とも変換できたときだけ位置を保存し、できなければ最後の正しい位置を使う。

描き方は、祠に立っていないときのワールドマップに合わせた。

| 状態 | 表示 |
| --- | --- |
| 陣営が所有 | 所有陣営の色、不透明度 0.8 |
| どの陣営も所有していない | 不透明度 0.2 |
| `FAST_TRAVEL_LINK_IN_COMBAT`（戦闘で寸断） | 破線 `AvA_transitLine_dashed.dds` |
| それ以外 | 実線 `AvA_transitLine.dds` |

祠に立っているときだけワールドマップが使う「自分が今使える経路を緑に」という色分け
（`GetKeepFastTravelInteraction()` 中のみ）は、HUDでは祠にいないので採っていない。
線の配置はクライアントの `ZO_Anchor_LineInContainer`（TOPLEFT を始点、BOTTOMRIGHT を終点に
アンカーする）と同じことを自前で書いており、クライアントの関数は呼んでいない。
太さはワールドマップの 8（数千単位幅の地図での値）ではなく、地図の大きさに比例させた。

### 設定パネルを Map.lua に依存させない

最初の実装では、地図の位置・重なり順の行が `self.map:Position()` を読んでいた。Map.lua が読み込めない
環境ではスタブにその関数が無く、**設定パネル全体が落ちる**（「全行の getFunction を呼ぶテスト」が検出）。
パネルの行は保存値と既定値だけを読み、上限・下限の定数も Main.lua に置いた。

## 表示位置の範囲は画面サイズから決める

4つの表示面（通知・戦況・出力ウィンドウ・全体マップ）は、どれも「基準位置＋左右・上下のずらし」で
置く。ずらしの範囲は当初 ±900 × ±500 の固定値で、たとえば右上基準だと左へ900までしか動かせず、
1920幅の画面でも左半分に届かなかった。

範囲は `GuiRoot:GetDimensions()` の幅・高さそのもの（正負両方向）にした。UIスケールで画面の
論理サイズが変わるため固定値は使わない。これでどの基準位置からでも画面のすべての点に届く。
設定パネルのスライダーはこの値を範囲にするので、パネル生成（`EVENT_PLAYER_ACTIVATED`）の直前に
読み直す。取得できない場合は 1920 × 1080 を使う。

## 状態遷移（「防衛成功」と「防衛失敗」の見分け方）

自陣営の拠点が攻撃を受けたときだけエントリを作り、攻撃が終わったら消す。通知はすべてこの遷移である。

```
エントリ無し + 自陣営 + 攻撃中     -> 赤（監視開始）
エントリ有り + 自陣営 + 攻撃中     -> 赤（再通知間隔を超えていれば）
エントリ有り + 自陣営 + 攻撃終了   -> 青（防衛成功）
エントリ有り + 自陣営 -> 他陣営    -> 黄（防衛失敗 + 奪った陣営名）

エントリ無し + 敵拠点 + 攻撃中     -> 緑（戦闘開始。オプション、初期オフ）
エントリ有り + 敵拠点 + 攻撃中     -> 緑（再通知間隔を超えていれば）
エントリ有り + 敵拠点 -> 自陣営    -> 青（占領成功）
エントリ有り + 敵拠点 + 攻撃終了   -> 何も言わずにエントリだけ破棄
```

最後の1行だけ非対称なのは意図的である。他陣営の拠点での戦闘が「その拠点が他陣営のまま」終わっても、
自分のキャンペーンに関して変わったことは何も無い。逆に占領した場合は**続けて2行出るのが正常**で、
「占領しました（青）」の直後に「攻撃を受けています（赤）」が来る。取られた側がすぐ殴り返してくるため、
占領直後の拠点は自陣営の攻撃中拠点そのものになる。

**重要: 「奪われた」は攻撃フラグではなく所有陣営で判定している。** 落ちた直後の拠点はたいてい
`GetKeepUnderAttack` が true のままである（味方がすぐ取り返しに殴っているため）。攻撃フラグが落ちるのを
待つと、防衛失敗の通知が出ないか、何分も遅れる。

自陣営でない拠点は最初から監視対象外なので、「敵から取り返した拠点がまた攻められている」は
単に新しい攻撃として赤で出る。これで正しい。

## 画面表示（HUD）に使ったもの

チャット欄以外に出す手段として、トップレベルウィンドウ1枚＋ラベル1個を作っている。
クライアント自身が同じ手順を踏んでいる（`housingeditorhud.lua:1145` 付近）。

```lua
local window = WINDOW_MANAGER:CreateTopLevelWindow(name)
window:SetAnchor(point, GuiRoot, point, x, y)
window:SetMouseEnabled(false)
local label = WINDOW_MANAGER:CreateControl(name .. "Text", window, CT_LABEL)
label:SetFont("$(BOLD_FONT)|32|soft-shadow-thick")
```

判断したこと:

- **ラベルは1個。** ラベルのテキストはチャットと同じ `|cRRGGBB` マークアップを解釈するので、
  3色3行を1コントロールに入れられる。行ごとにコントロールを作ると、生成・アンカー・破棄が
  毎回必要になり、それは `\n` が既にやっていることの再実装でしかない。
- **マウスは常に無効。** コントローラ環境でオーバーレイが本当に害になるのは、下のゲームから
  クリックを奪ったときだけ。ドラッグでの位置調整をやめて設定パネルに寄せたのも同じ理由。
- **重なり順は3段階から選べる（戦況表示のみ）。** クライアント自身が実行時に切り替えている
  （`ZO_KeybindStrip:SetDrawOrder`、`zo_keybindstrip.lua:180`）ので、2つの列挙の両端と中央を
  そのまま割り当てた。最前面 = `DL_OVERLAY`/`DT_HIGH`、標準 = `DL_CONTROLS`/`DT_MEDIUM`、
  最背面 = `DL_BACKGROUND`/`DT_LOW`（ハウジングエディタのインジケータと同じ、
  `housingeditorhud.lua:1151`）。`board:Apply()` から毎回適用している。設定を変えた後に
  ウィンドウが生成される順序（ログイン直後がこれ）でも選択が効くようにするため。
- **`SetDrawLayer` / `SetDrawTier` は `pcall` で囲んで呼ぶ。** APIダンプでは
  *protected-attributes* だが、このダンプのマーカーは両方向に間違っていた実績があり、
  実際に配布されているアドオン（Votan's Minimap の `PinLevels.lua:33`）は `SetDrawLevel` を
  呼んでいる。呼ぶ／呼ばないを決め打ちせず、失敗しても表示が消えるだけで済む形にした。
  拒否された場合は `drawOrderRefused` を立て、`/pbalert` とコマンドの応答がその旨を表示する
  （設定が効いたように見えるのを避けるため）。
- **書体はPB's QuestTrackerFontChanger と同じ5つに限定。** PS5で実測済みの制約をそのまま
  引き継いでいる。ANTIQUE_FONT / HANDWRITTEN_FONT / STONE_TABLET_FONT / CHAT_FONT は
  UIが他で描画に使っておらず、使用時に構築が走ってアドオン共通のメモリを食い、落ちる。
  エイリアス（`$(BOLD_FONT)`）で持ち、解決済みパスは使わない。日本語クライアントで
  日本語の拠点名が描ける書体が返るのはエイリアス経由だけ。
- **縁取りはトークン文字列**（`thick-outline` など）であって `FONT_STYLE_*` の数値ではない。
  `SetFont` が `face|size|style` を解釈する。クライアントのfontdefsに実在する4種類だけを提供。

## 出力ウィンドウ

アドオンの出力（通知・コマンド応答・一覧・戦況すべて）を専用ウィンドウに出す。理由は
チャット欄が埋まること。コンソールにはタブによる振り分けが無いので、会話がアドオンの実況で
流れてしまう。

- **経路は1本にした。** `Say()` が唯一の出口で、`Line` / `Print` / `Emit` はすべてここを通る。
  「どこに出すか」を1か所の判断にするため。
- **ウィンドウが受け取ったかどうかを `Push` が返す。** 受け取らなければチャット欄に出す。
  出力先が chat のとき、ウィンドウを作れなかったとき、どちらも同じ経路で救われる。
  **アドオンが自分の出力を黙って捨てることだけは避ける。**
- **新しい行が上。** これは好みではなく、はみ出さない唯一の並び。ラベルの
  `SetMaxLineCount` は先頭からN行を残すので、新しい行を下に積むと、折り返しが1回起きた瞬間に
  一番新しい行が切られる。上に積めば、あふれるのは常に一番古い行になる。
- **背景板（`CT_BACKDROP`）を敷けるようにした。** 縁取りだけでは砦の壁を背景にしたときに
  読めないため。濃さは0〜100%で、0なら板ごと隠す。
- **重なり順は戦況表示と同じ3段階から選べる**（最前面／標準／最背面）。2つのウィンドウは
  それぞれ独立した設定を持ち、`board:Apply()` / `log:Apply()` から毎回適用する。
  拒否された場合も同じく `drawOrderRefused` を立てて `/pbalert` が報告する。
- **シロディールと帝都の外では非表示。** 空にするのではなくウィンドウごと消す。街やトライアルの
  画面にアドオンの出力パネルが載っているのは邪魔でしかない。出力は止めず、チャット欄に回す。
  再入場時は空の状態で出す（1時間前の通知が復活するのはログではなく幽霊）。
  これは監視側の `onlyInAvA` とは別の判断で、あちらは「キャンペーンを読むか」、
  こちらは「ウィンドウを置いてよい場所か」を決める。
- マウスは他の2面と同じく無効。ドラッグで動かせない代わりに、大きさ・位置は設定にした。
  コントローラ環境で「掴めるウィンドウ」はいずれキーバインドを食う。

画面表示は**全体が任意**である。`WINDOW_MANAGER` が無い、あるいはウィンドウ生成に失敗した場合は
`Available()` が false を返し、`/pbalert` がそう表示し、通知はチャット欄にだけ出る。
`Hud.lua` を丸ごと外してもアドオンは動く（`Main.lua` 側に何もしないスタブが入っている）。

## 戦況の数値をどこから取るか

クライアント自身のスコアボード（`campaignscoring_shared.lua:44` `UpdateScores`）と同じ関数を使う。

```lua
local campaignId = GetCurrentCampaignId()
GetCampaignAllianceScore(campaignId, alliance)                      -- 得点
GetTotalCampaignHoldings(campaignId, HOLDINGTYPE_KEEP, alliance)    -- 砦の数
GetTotalCampaignHoldings(campaignId, HOLDINGTYPE_OUTPOST, alliance) -- 前哨の数
GetCampaignEmperorInfo(campaignId)                                  -- 皇帝の陣営と名前
GetCampaignName(campaignId)
```

自前で数えるのではなくこれを使うのは、**マップやスコアボードと数字が食い違わないため**。
`GetAvAKeepsHeld` でも砦数は取れるが、クライアントが実際に表示に使っているのは
`GetTotalCampaignHoldings` の方だった。

### 人口（各同盟の在籍状況）

シロディール入場時のキャンペーン選択画面に出るものと同じ推定値で、`GetSelectionCampaignPopulationData`
から取る。**人数ではなく4段階**（低 / 中 / 高 / 満杯 = `CAMPAIGN_POP_LOW/MEDIUM/HIGH/FULL`）。
ゲームは実数をどこにも公開していないので、段階を人数に変換する手段は無い。

2点、他の数字と違う扱いが要る。

- **キャンペーンIDではなく「選択インデックス」で引く。** 別のテーブルなので、
  `GetNumSelectionCampaigns()` を回して `GetSelectionCampaignId(i)` が現在のIDと一致する行を
  探す（`campaignbrowser_manager.lua:223` も同じ歩き方をしている）。
- **そのテーブルはサーバーへの問い合わせで埋まる。** `QueryCampaignSelectionData()` は
  キャンペーンブラウザが開くたびに投げているのと同じリクエスト。5秒ごとの走査から素直に呼ぶと
  5秒ごとのサーバーリクエストになるので、**5分に1回まで**に制限した。4段階の推定値はそれより
  速く動かない。
  - 当初は「データが**無いとき**だけ」頼んでいた。そのため一度取れると以後は誰も頼まず、
    サーバーが自発的に更新を送ってこない限り（送る根拠は見つかっていない）、入場時の混雑度が
    出続けていた。データの有無に関係なく5分ごとに頼む形に直した（2.5.2）。
  - 頼むのは戦況表示がオンの間だけ。見られていない表示のために通信はしない。
    `/pbalert board` で直接表示を求めた場合は、オフでも頼む（間隔の制限は同じ）。
  - `/pbalert` に「混雑度の最終更新: ○前」を出す。実機で本当に更新されているかの計測用。答えは `EVENT_CAMPAIGN_SELECTION_DATA_CHANGED` で受けて
  再描画する（プレイヤーが自分でブラウザを開いたときの更新もこれで拾える）。

表示は**ゲーム自身のキャンペーンブラウザのアイコン**を使う。パスは
`ZO_CampaignBrowser_GetPopulationIcon(population)`（`campaignbrowser_manager.lua:433`）から取り、
`zo_iconFormat(path, "100%", "100%")` でラベル用の `|t|t` マークアップにする。

- **サイズは "100%"**。ピクセル指定ではないので、画面表示のフォントサイズを変えても、
  チャット欄に出しても、その場の行の高さに追従する。サイズ設定を増やさずに済む。
- **取得は3段構え。** クライアントの getter →（無ければ）アドオン内のパス表 →
  （マークアップを作れなければ）文字。アイコンが出せない環境で列が空白になるのを防ぐ。
  パスを直書きだけにしないのは、アートの移動に getter が追従するため。
- 文字にしたい場合の設定も用意した（`/pbalert board pop text`）。

段階名（文字表示時）は**定数ごとに文字列IDを手で対応付ける**。

```lua
DeclarePopulationWord(CAMPAIGN_POP_LOW,    SI_CAMPAIGNPOPULATIONTYPE0)
DeclarePopulationWord(CAMPAIGN_POP_MEDIUM, SI_CAMPAIGNPOPULATIONTYPE1)
...
```

最初は `GetString("SI_CAMPAIGNPOPULATIONTYPE", 値)`（クライアント自身の引き方、
`campaignbrowser_manager.lua:168`）を使っていたが、**実機で全段階が1つ上にずれた**
（低→中、高→満杯）。文字列の接尾辞は0始まりで、`CampaignPopulationType` の数値はそうではない。
この引き方は「列挙型の数値と接尾辞が一致している」ことが前提で、ここではそれが成り立たない。

拠点の種類やマップピンと同じく、定数を直接キーにすれば数値が何であっても壊れない。
テストのハーネスも `CAMPAIGN_POP_LOW = 1` から始まる**わざと接尾辞と揃わない**数値にしてあり、
数値から文字列を導く実装に戻すとテストが落ちる。

アイコンはゲームパッドUIとキーボードUIで別のアートを使っている
（`campaignbrowser_gamepad.lua:241` はファイルローカルなのでパスを直書き）。コンソールで
プレイヤーが直前に見ているのはゲームパッド側なので、`IsInGamepadPreferredMode()` で切り替える。

**「攻撃中」の列だけはクライアントに無い。** 「ある陣営の拠点のうち何箇所が攻撃を受けているか」を
返すAPIは存在しないので、これはアドオン自身の走査で数えている（アラート用のループに相乗り
させたので、追加コストは実質ゼロ）。マップを開かずに画面に出す価値があるのは、まさにこの列である。

段階的に劣化させてある:

| 状況 | ふるまい |
| --- | --- |
| キャンペーンID = 0（未所属・未受信） | 拠点数はアドオン自身の集計にフォールバック、得点は `-` |
| シロディール外・監視オフ | **表示を消す**（得点は正しいまま「攻撃中」だけ凍った状態が一番悪い） |
| 走査が1回も終わっていない | 何も描かない（0を並べない） |

陣営色は `GetAllianceColor(alliance):ToHex()`。`ToHex` はアルファを不透明に固定して
`"rrggbb"` の6桁を返す（`zo_colordef.lua:182`）が、ユーザー入力の色と同じ検証を通している。
`|c` の桁が狂うと行頭の文字が食われるという壊れ方をするため。

## 色の指定

`|cRRGGBB` は**6桁の16進数でなければ黙って壊れる**。`|cFF40` のように桁が足りないと、
続く文字が色コードとして食われて行頭が欠ける。設定として受け取る以上ここは検証が要るので、
`NormaliseHex` を通らない値は保存しない（パレット名でも16進でもなければコマンドが拒否する）。

色は「通知の種類 × 出力先」で持っている。チャット欄は暗い背景の上、画面表示は景色の上に出るため、
同じ色が両方で読めるとは限らないため。

ただし**初期状態では画面表示はチャット欄の色を参照する**（`hudFollowsChatColours`、初期オン）。
値をコピーするのではなく参照にしてあるので、あとからチャット欄側を変えても同期処理なしで追従する。
画面表示側の色を指定した時点で参照はオフになる。参照したまま値だけ保存すると、
設定したのに反映されないという一番良くない結果になるため。パネルの各行は
`Colour()` の結果（＝実際に描画されている色）を返すので、参照中は行がチャット欄の色を表示する。

## シロディール外では何も動かさない

初期設定（`onlyInAvA`）では、AvAゾーンの外で**タイマー自体を停止**する。走査が空振りするのではなく、
`RegisterForUpdate` の登録を外す。判断は1か所（`ShouldWatchHere`）に集約し、そこを通る入口も
`ApplyTimer` の1つだけにした。

停止／再開のきっかけは `EVENT_PLAYER_ACTIVATED`。ゾーン移動のたびにクライアントが必ず送るもので、
この時点ではワールドが読み込み済みなので `IsInAvAZone()` が答えられる。

- セッションの大半はシロディールの外なので、その間のコストがゼロになる
- 停止時は監視状態と戦況の集計も破棄する。戻ってきたときに、別の場所の記憶から
  「終了」を報告してしまうのを防ぐため
- `Scan()` にも同じ判定を残してある（`/pbalert` から直接呼べるため）。ただし判定を
  `GetNumKeeps()` の**前**に移した。見えないと分かっている場所で拠点一覧を歩く必要はない

`ava off` にすればどこでも走る。その場合の挙動は従来どおり。

## 表示名のアポストロフィ

**設定パネルに渡す名前は U+2019（`’`）でなければならない。** ASCII の `'` にすると
LibHarvensAddonSettings が「PB's 」ごと落とし、パネル名が `CyrodiilAlert` になる。

一方、ゲーム内アドオン一覧に出る名前はマニフェストの `## Title` が供給していて、こちらは
ASCII で正しく表示される。したがって**2か所で1文字だけ違う**:

| 表示場所 | 供給元 | アポストロフィ |
| --- | --- | --- |
| アドオン一覧 | `## Title` | ASCII `'` |
| 設定パネル・チャット接頭辞 | `DISPLAY_NAME` | U+2019 `’` |

他のPB'sアドオンはすべて `DISPLAY_NAME` に U+2019 を入れており、それらのパネル名は正しく出ている。
これは表記の好みではなくライブラリの制約である。

**Lua 5.1 なので `"\u{2019}"` は使えない**（5.3 の構文）。ソースには文字そのものを書く。
ローカルのテストは新しい Lua で走るため、エスケープを書くとテストだけ通って実機で構文エラーになる。

テストは `PanelTitle`（ライブラリに渡した文字列）を直接検証する。なお、この検証を
`sub(1, 4)` で書くと落ちる。U+2019 は3バイトで、バイト位置と文字位置がずれるため。

## 設定パネルの行は「読める」ことまで確かめる

LibHarvensAddonSettings は行を生成するときと更新するときに `getFunction` を必ず呼ぶ。
**1行でも nil を返すか例外を投げると、設定パネル全体が落ちる**（実機で発生。スライダーの
読み取り関数名を設定項目名から機械的に組み立てていて、`lines` → `log:Lines()` を探しに行った。
実際の名前は `MaxLines` だった）。

対策は2つ入れた。

- 読み取りから推測をなくした。保存値をそのまま返し、無ければ既定値を返す。
- **全行の `getFunction` を呼ぶテスト**を追加した。1行ずつ書くのではなく `PanelRows` を
  総なめするので、今後追加する行も自動的に対象になる。スライダーは「設定した値がそのまま
  読み戻せるか」も併せて確認する。

## 分からないときは黙る

| 状況 | ふるまい |
| --- | --- |
| 拠点APIがないクライアント | タイマーを起動しない。`/pbalert` がそう言う |
| AvAゾーン外 | 走査を飛ばし、監視状態を破棄する（戻ってきたら読み直し） |
| 拠点が一覧から消えた（キャンペーン変更など） | 終了通知を出さずにエントリだけ破棄。どう終わったか分からないため |
| 名前が取れない | keepId を表示（空欄にはしない） |

唯一の割り切り: **経過時間はアドオンが攻撃を見つけた時刻からの計測**であり、攻城戦の開始時刻ではない。
攻撃中の拠点があるところへ入場した場合、「3:20経過」は監視して3分20秒という意味になる。

## 未検証（PS5での実測が必要）

オフラインテスト（`lua test/run.lua`、434項目）は状態遷移・色・キャンペーンのふるい・タイマー再登録に加え、
画面表示（どの行が出るか、色・書体・位置、期限切れ、ウィンドウ生成失敗時の退避）と
戦況表示（数値・並び順・陣営色・劣化時の各分岐）も通っているが、
**実機では未確認**。実機で最初に確かめるべきは次の1点:

> シロディールに入って `/pbalert list` を打つ。
> クライアントが報告している拠点数、うちこのキャンペーンの件数、監視対象件数と、
> 各拠点の所有陣営・攻撃状態が出る。

- 3つの数字がすべて0 → キャンペーンのふるい（`IsLocalBattlegroundContext`）か、そもそも拠点APIが
  この環境で空を返している。
- 総数だけ出て「このキャンペーン」が0 → ふるいが強すぎる（`BGQUERY_ASSIGNED_CAMPAIGN` 側しか
  返っていない）。ここが分かれば直し方が1つに決まる。
- 数字が妥当で所有陣営も正しい → 読み取りは効いている。あとは実際の攻城戦を待てばよい。

画面表示については `/pbalert test` が用意してある。攻城戦を待たずに5種類を1回ずつ出すので、
書体・サイズ・位置・色の確認はこれで完結する。ここで**何も画面に出ない**場合は
`/pbalert` の「画面表示: ...」の行を見ること。`このクライアントでは画面表示を作成できませんでした`
と出ていればウィンドウ生成の失敗（`SetDrawLayer` を含めて全部 `pcall` の内側なので、
アドオン自体は動き続ける）、出ていなければ種類の選択が空か、位置が画面外である。

もう1点、緑の通知（敵拠点での戦闘）を使う場合に確かめる価値があるのは**攻城兵器の数が遠くの拠点でも
届いているか**である。`/pbalert list` は各拠点に「自陣営の攻城兵器 N基」を併記する。自陣営が明らかに
攻城中の拠点で常に空欄なら、この数字はこの環境では当てにならず、緑の通知は「戦闘が始まった」以上の
ことを言えない、と判断できる。

`/pbalert` の状態表示は毎回**実際の走査を1回走らせて**その結果を出しているので、
「表示は出るが通知が来ない」という食い違いは起きない。
