# 特定プレイヤーの視認性を上げるために、アドオンに何ができるか — 調査結果

調査対象: `esoui/esoui`（live ブランチ、2026-09-28 時点）の Lua / XML ソースと `ESOUIDocumentation.txt`。
頭上ネームタグそのものの調査は `PBsNamePlateChanger/FINDINGS.md` にあり、ここではその続きを書く。

## 結論

| やりたいこと | できるか | 理由 |
| --- | --- | --- |
| 頭上ネームプレートの文字色を変える | **できない** | 描画はエンジン。色の setter が API に存在しない |
| 頭上ネームプレートを四角で囲む | **できない** | 下記「位置が取れない」 |
| ネームプレートの上にマークを出す | **できる見込み（1.1.0 で「表示された」と報告あり。どの経路かは未確認）** | ゲーム標準のターゲットマーカーを付ける。`AssignTargetMarkerToReticleTarget` |
| レティクルを合わせなくても、視界に入った時点でマークを出す | **できない** | 下記「付けられるのはレティクルの先の1体だけ」 |
| ターゲット枠・グループ枠の名前の色を変える／枠で囲む | できたが、1.2.0 で削除 | 1.1.0 まで実装。不要とのことで撤去 |

## ネームプレートの上のマーク

頭上のネームプレートの上にマークを出せる唯一の手段は、エンジンが描いている**ターゲットマーカー**そのもの
（設定 > ネームプレート > ターゲットマーカー）を使うこと。ゲーム自身のマーカーホイール
(`ingame/targetmarker/targetmarkerwheel_shared.lua`) は、選択された項目で
`AssignTargetMarkerToReticleTarget(markerType)` を呼ぶだけで、これと同じ呼び出しをアドオンから行う。

- クライアントは、マーカーの付いたユニットの名前の前に、そのアイコンを自分で入れる
  (`unitframes.lua` の `UpdateName`、`GetUnitTargetMarkerType`)。だからターゲット枠・グループ枠には
  アドオンが何も描く必要が無く、コントロールへの書き込みも、フックも、タイマーも不要になった。
- マーカーの種類は**同時に1体にしか付かない**。全員共通の1種類にしているので、複数人を登録していると
  最後に見た1人に移る。
- 既に何かのマーカーが付いている相手には付けない（他人が付けたものを奪わない）。ただし、同じセッションで
  アドオン自身が付けた種類のマーカーは「自分のもの」とみなし、設定でマークを変えたときは付け替える。
- 同じマーカーを同じ相手に二度付けると外れる可能性があるので、付けるのは「接触ごとに1回」だけ、
  同じプレイヤーには 3 秒の再試行間隔を置く。タイマーから付けないのも同じ理由（サーバーの返事が来る前に
  二度目を撃たない）。
- `SI_TARGET_MARKER_INVALID_TARGET_ALERT`（「ターゲットマーカーを付けられない対象です」）があり、
  付けられない相手がいる。どういう相手かは未測定。
- 削除してもマーカーは外れない。API に「レティクルの先にいない相手から外す」手段が無い。

### 付けられるのはレティクルの先の1体だけ

`AssignTargetMarkerToReticleTarget` の引数はマーカーの種類だけで、**ユニットを指定できない**。
ドキュメント全体に、ユニットを指定してマーカーを付ける関数は無い（`TargetMarker` を含む関数は
`GetUnitTargetMarkerType` と `AssignTargetMarkerToReticleTarget` の二つだけ）。

さらに「視界に入った」ことを知る手段も無い。

- unitTag を持つのは `player` / `group1..24` / `reticleover` / `boss` / `companion` 系だけ。
  `EVENT_UNIT_CREATED` / `EVENT_UNIT_DESTROYED` もその unitTag 向けで、周囲の非パーティのプレイヤーには
  発火しない。
- 周囲のプレイヤーを列挙する API は無い。
- 戦闘イベント（`EVENT_COMBAT_EVENT` など）は、自分やグループが関わる相手の名前までは分かるが、
  マーカーを付ける手段が無い以上、検知できても意味が無い。

したがって「レティクルを合わせなくても付ける」は API の制約で不可能。成立するのは、
**一度レティクルを合わせたあと、ゲームがマーカーを表示し続ける**部分だけ。マーカーが離れたあとも
相手に残るかどうかはゲーム側の挙動で、アドオンからは制御できない。

## 「視界にいるだけの相手」を検知・描画できるか — 再調査（2026-10-20）

「画面に見えているのだから判別できそうなもの」という指摘を受けて、API を網羅的に当たり直した。結論は変わらない。
根拠は次の4点。

1. **unitTag の種類が限られている。** クライアントの Lua 全体が使う unitTag は `player` / `group` 系
   (`group1`…)・`reticleover`（`reticleovertarget` / `reticleoverplayer` / `reticleovercompanion`）・
   `boss`・`companion`・`interact` だけ。他の人間のプレイヤーに割り当てられる unitTag は、グループとレティクル以外に無い。
2. **位置を返す関数は、全て unitTag を取る。** `GetUnitWorldPosition` / `GetUnitRawWorldPosition` /
   `GetMapPlayerPosition`（いずれも引数は unitTag）。名前や ID から位置を引く関数は無い。
3. **周囲のプレイヤーを数え上げる関数・イベントが無い。** 名前に `Nearby` / `InRange` / `Visible` /
   `AllPlayers` などを含むものを調べたが該当なし。`EVENT_UNIT_CREATED` / `EVENT_UNIT_DESTROYED` の引数も unitTag。
4. **ユニットを指定してマーカーを付ける関数が無い。** `TargetMarker` を含む関数は `GetUnitTargetMarkerType` と
   `AssignTargetMarkerToReticleTarget` だけ。

描画側の手段も確かめた。ワールドに浮かぶマーカー（フローティングマーカー、`SetFloatingMarkerInfo`）や
マップピン（`AddMapPin`）は、クエスト・グループなどのピン種別と、その識別用の整数から**エンジンが位置を決める**。
任意のワールド座標に置けるのは、プレイヤー自身のウェイポイント (`SetPlayerWaypointByWorldLocation(x, y, z)`) だけで、
位置が分かる相手が前提になる。座標を取れる相手は「グループのメンバー」と「レティクルが当たった相手」だけ。

### 残った現実的な手段

| 手段 | 対象 | 状態 |
| --- | --- | --- |
| ゲーム標準のターゲットマーカーを、レティクル接触時に付ける | レティクルが一度当たった相手 | 実装済み（1.2.0）。離れたあとも残るか、**コンパスに出るか**は未測定 |
| 頭上マーカーと画面端の方向矢印を自前で描く | **同じグループにいる相手** | 位置が取れるので可能。未実装 |
| キルフィード・戦闘イベントに名前が出たら、音と画面で知らせる | キルフィードに載る相手／自分やグループと戦闘上の関わりがある相手 | **実装済み（1.3.0）**。イベントがどこまで届くかは未測定 |
| レティクル接触時の位置にウェイポイントを置く | 一度見た相手の「最後に見た場所」 | 可能。ただし自分のウェイポイントを占有し、相手が動けばずれる |

ターゲットマーカーは、設定に「コンパスのターゲットマーカー」(`UI_SETTING_COMPASS_TARGET_MARKERS`) があり、
コンパスへの表示はエンジンが管理している。マーカーを付けた相手の方向がコンパスに出るなら、一度の接触のあとは
離れていても方向が分かる。これが成立するかが、今のところ最も大きい未測定事項。

## フレンド・ギルド以外の相手の居場所（1.6.0 の再調査）

「フレンド・ギルド仲間以外の居場所は取得できない」と断言したのは言い過ぎだった。正確には次のとおり。

| 知りたいもの | 取れるか | 手段 |
| --- | --- | --- |
| 座標（位置） | **取れない**（グループ・レティクル以外） | 位置を返す関数は全て unitTag を取る |
| いまいるゾーン | フレンド・ギルドメンバーのみ | 名簿 API。名簿に載らない相手は取れない |
| 最後に見かけた場所と時間 | **取れる（登録した全員）** | 下記の目撃記録 |

**ジャンプ（Travel to Player）から居場所が分かるのでは、という見立てについて。** ゲームのジャンプ関数は
`JumpToFriend` / `JumpToGuildMember` / `JumpToGroupMember` / `JumpToGroupLeader`（と、プレイヤーの家へ飛ぶ
`JumpToHouse`）だけで、スラッシュコマンドも同じ4つ。UI で「プレイヤーのもとへ移動」が出るのも、フレンドリスト・
ギルド名簿・グループ一覧だけ（`friendslist_*`、`guildroster_*`、`zo_grouplist_*`）。つまり**名簿の外の相手には
そもそも飛べない**ので、ジャンプの裏に「全プレイヤーの居場所」があるわけではない。名簿の相手の居場所は、
すでに名簿 API で取っている。また、ジャンプは実際に移動する操作で、調べるための関数ではない。
`CanJumpToPlayerInZone(zoneId)` という判定関数もあるが、Lua のクライアントコードからは一度も使われておらず、
引数がゾーンIDで相手の名前を取らないので、特定のプレイヤーを調べる手段にはならない。

**目撃記録**（`Sighted`）— 登録したプレイヤーに行き当たるたびに、最新の1件を覚える（セッション中のみ）:

| 行き当たる場所 | 分かること | 場所の出どころ |
| --- | --- | --- |
| キルフィード `EVENT_PVP_KILL_FEED_DEATH` | 倒した／倒された。**「near ＜砦の名前＞」** | イベントの `killLocation` |
| 戦闘イベント | 近くで戦闘している | 自分のいるゾーン |
| `/say`・`/yell`・エモート（`EVENT_CHAT_MESSAGE_CHANNEL`） | 声の届く範囲＝近く | 自分のいるゾーン |
| ゾーンチャット | 同じゾーン | 自分のいるゾーン |
| レティクルが当たった | その場にいる | 自分のいるゾーン |

ゲーム自身の説明に、キルフィードは「近くのプレイヤーが倒されたときに表示」とあり
（`SI_SOCIAL_OPTIONS_SHOW_PVP_KILL_FEED_NOTIFICATIONS_TOOLTIP`）、書式は「X defeated Y **near ＜場所＞**」
（`SI_PVP_KILL_FEED_DEATH_AND_LOCATION`）。メッセージには「ローカル由来」と「撃破地点由来」の2種類
（`isKillLocation`）があり、後者が砦の名前を運ぶ。チャットのイベントは送信者の `@アカウント名` も運ぶので、
@アカウント名で登録した相手はそのまま一致する。本文は読まない。

**「擬似的に名簿へはめる」ことはできるか（1.6.0 の追加検証）。** できない。名簿（フレンド・ギルド・グループ）の中身は
サーバーが持つデータで、クライアントのアドオンから書き込める場所が無い。名簿に入る正規の手段は、いずれも
**相手の同意が要る**操作だけ。

| 名簿 | 入れる手段 | 相手の同意 |
| --- | --- | --- |
| フレンド | `RequestFriend(名前, メッセージ)` を送り、相手が `AcceptFriendRequest` | 要る（申請は相手に通知される） |
| ギルド | 同じギルドに入る（招待・ギルドファインダーの申請） | 要る（招待または承認） |
| グループ | `GroupInviteByName` を送り、相手が承諾 | 要る |

同意なしで使える「自分側だけの一覧」も確かめたが、居場所は返さない。
- 無視リスト: `GetIgnoredInfo(i)` が返すのは `displayName` と `note` だけ（`ignorelist_shared.lua` もその2つだけで
  行を作っている）。状態・キャラクター・ゾーンを返す関数は無い。`EVENT_IGNORE_ONLINE_CHARACTER_CHANGED` という
  イベントはあるが、引数は表示名だけで、クライアントの Lua からも使われておらず、読み出し側の関数も無い。
- 送信済みのフレンド申請: `GetOutgoingFriendRequestInfo(i)` は `displayName`・申請からの秒数・メモだけ。
  承諾されるまでは名簿に入らない。
- 最近いっしょにいた人・近くの人といった一覧は、API に存在しない。

アドオンは、相手に届く働きかけ（フレンド申請、グループ招待）を自動では行わない。ゲームのメニューから本人が
行ってよい操作だが、相手に通知が出て、相手が拒否できるものだから。相手が承諾して名簿に入れば、このアドオンは
追加の操作なしに居場所を追い始める（名簿の走査とゾーン変更イベントは、登録名が名簿にあれば自動で効く）。

**ほかに調べて、使わなかったもの。**
- `EVENT_ARTIFACT_CONTROL_STATE`（エルダースクロールの取得・ドロップ。運搬者の名前と砦ID）: 場所が「そのスクロールの
  砦」で運搬者の現在地とは限らず、意味が曖昧なので見送り。
- マップピン: `MAP_PIN_TYPE_*` を全て確認したが、任意のプレイヤーを表すものは無い（`PLAYER` は自分、`GROUP` は
  グループ）。`TARGET_MARKER_TYPE_ONE`〜`EIGHT` はピン種別として存在するが、ワールドマップの Lua
  （`mappin_manager.lua`）は扱っておらず、コンパス表示はエンジン内部。
- 友達申請（`RequestFriend`）やグループ招待: 相手が承諾すれば名簿／グループに入って位置まで分かるが、
  相手に届く働きかけであり、勝手には行わない。

## 居場所とシロディール入り（1.5.0）

「いまどこにいるか」と「シロディール入りの通知」は、**フレンドとギルドメンバーに限って**可能。ゲームが
全プレイヤーのうちこの2つのグループだけ、居場所を名簿として報告しているため。

- `GetFriendInfo(i)` → 表示名・状態・最終ログアウトからの秒数。`GetFriendCharacterInfo(i)` → キャラクター名・
  ゾーン名・クラス・同盟・レベル・CP・**ゾーンID**。ギルドは `GetGuildMemberInfo` /
  `GetGuildMemberCharacterInfo`（ギルドID＋メンバー番号）で同じもの。
- イベント: `EVENT_FRIEND_CHARACTER_ZONE_CHANGED`（表示名・キャラクター名・ゾーン名）、
  `EVENT_GUILD_MEMBER_CHARACTER_ZONE_CHANGED`、`EVENT_FRIEND_PLAYER_STATUS_CHANGED`、
  `EVENT_GUILD_MEMBER_PLAYER_STATUS_CHANGED`。ゾーン変更イベントはゾーン**名**しか運ばないので、名前で
  シロディールか判定する。オンライン化のイベントはゾーンを運ばないので、名簿を引き直す。
- **分かるのはゾーンまで。** 座標は無いので、どの砦かは分からない。
- **フレンドでもギルド仲間でもない相手は、どの API でも居場所が分からない。** 名簿に載っていないため。
  `where` はその旨を表示する。
- シロディールの判定: ゾーンIDを数値で埋め込まず、`GetCyrodiilMapIndex()` → `GetMapInfoByIndex()` の
  zoneIndex → `GetZoneId()` でゲームに聞く。名簿のゾーンIDがそれか、`GetParentZoneId()` がそれなら
  シロディール内。それでも決まらないときはゾーン名で比較する。
- 名簿の探索: 友達は少ないので表示名・キャラクター名を一度に調べる。ギルドは最大5ギルド×500人ほどなので、
  まず表示名（安い）で全員を調べ、見つからない登録プレイヤーがいるときだけ、キャラクター名で二周目を行う。
  結果は 10 秒キャッシュし、設定画面が1行ずつ尋ねても1回のスキャンで済ませる。
- **通知は「入った」瞬間だけ。** 「シロディールにいない（または不明）」→「いる」を検知し、プレイヤーごとに
  30 秒のクールダウン。ログインの 20 秒後に一度スキャンして、すでにいる人を記録する（到着として扱わない）。
- **枠の入れ替え**: 登録枠のプレイヤーが変わったら、その枠の「シロディールにいる」記録とクールダウンを消す。
  消さないと、前の人の状態が新しい人の到着を隠す（テストで見つけた不具合）。
- **名前のつなぎ**: PSN ID で登録した相手を名簿の `@アカウント名` に結びつけるため、レティクルが当たったとき
  （キャラクター名・@アカウント名・PSN ID の順）とキルフィード・名簿で一致したときに、その別名を登録枠に
  覚える（最大6つ）。

### 実機で確かめるべきこと（居場所）

1. `/pbtarget where` で、フレンド／ギルドメンバーの現在地が出るか。名簿の `displayName` が、PS5 でどの形式か
   （`@アカウント名` か PSN ID か）。見つからないなら、その名前の形式を教えてほしい。
2. `/pbtarget status` の `Cyrodiil zone id:` が数値になっているか（`?` ならゾーン判定の連鎖が失敗している）。
3. 登録した友達がシロディールに入ったとき、通知が出るか。
4. 名簿のスキャン（ギルド5つ分）で、体感できる引っかかりが出ないか。

## 通知（1.3.0）

敵・グループ外の相手向けに、ユーザーが選んだ手段。位置は分からないが、「その人がいる」ことは知らせられる。

- **キルフィード** `EVENT_PVP_KILL_FEED_DEATH`: 倒した側・倒された側の `@アカウント名`・キャラクター名・
  **場所（砦の名前）**が付く。チャットの「PvP キルフィード」設定とは無関係にアドオンへ届く
  （PBsKillLog が PS5 で使っているのと同じイベント）。@アカウント名で登録した相手にそのまま一致する。
  同じ1回のキルを2回報告してくる（`isKillLocation`）ので、プレイヤーごとに 4 秒のクールダウンで1回にまとめる。
- **戦闘イベント** `EVENT_COMBAT_EVENT`: 名前は**キャラクター名だけ**。ここに届くのは自分・グループ・ペットが
  関わるものと思われるが、どこまで届くかは**未測定**。エンジンのフィルタで「送信元（または対象）が他のユニット」
  のイベントだけを受ける（フィルタは AND なので、送信元用と対象用に2つ登録する）。プレイヤーごとに 20 秒の
  クールダウン。
- **@アカウント名とキャラクター名のつなぎ方**: レティクルが当たったとき、およびキルフィードで一致したときに、
  そのプレイヤーのキャラクター名を登録エントリに覚える（最大4つ。ID を変える／削除すると忘れる）。
  戦闘イベントはその名前で照合する。キャラクター名で直接登録すれば覚える必要は無い。
- **表示**: 自前の TopLevelControl（`PBsTargetPlayer.xml`）を `ZO_SimpleSceneFragment` で HUD シーンに載せる
  （PBsKillLog と同じ方式で、PS5 で実績あり）。フォントは `ZoFontGamepad34`（グループ枠が使っている面で、
  読み込み済み。未読み込みの面は使用時に構築されてアドオンのメモリを食い、PS5 で落ちた実績がある）。
  背景は色だけの Texture。入力は取らない。タイマーは通知が出ている間だけ。
- **音**: `SOUNDS.DUEL_START`（無ければ `NEW_NOTIFICATION`）。`/pbtarget test` で表示と音を単独で確かめられる。

### 実機で確かめるべきこと（通知）

1. `/pbtarget test` で、帯が画面上部に出るか、文字が読めるか、音が鳴るか。
2. 戦場で `/pbtarget status` を見る: `seen: kill feed N, combat M` が増えているか。増えない場合は、そのイベントは
   届いていない（その場合は通知は成立しない）。
3. 登録したプレイヤーがキルフィードに載ったとき、通知が出るか。場所の表示は正しいか。
4. 戦闘イベントでの通知は、一度レティクルを合わせたプレイヤーについてだけ効くはず。`learned names:` が増えているか。

## 頭上ネームプレートに手が出ない理由

- 色: `INTERFACE_COLOR_TYPE_NAME_PLATE` は `GetInterfaceColor` で読めるだけで、`SetInterfaceColor`
  はドキュメント全体に存在しない。ネームタグを描くコードも Lua 側には無い。
- **位置**: 頭上に自前のマークや枠を置くには相手のワールド座標が要る。座標を取れるのは unitTag を
  持つユニットだけで、周囲のプレイヤーは列挙できない。標準のネームタグを消す手段も無い
  （`SetSetting` は private）ので、出しても二重表示になる。

## private かもしれない関数を、どう安全に呼ぶか

`SetSetting` はドキュメントに表記が無いのに private で、`BindKeyToAction` は protected と書いてあるのに
実際は private だった。表記は当てにならない。private 関数を呼ぶと UI エラー画面が出て、`pcall` でも
止められない。そこで **呼ぶ前に API 自身に聞く**:

```
IsPrivateFunction("AssignTargetMarkerToReticleTarget")
IsProtectedFunction("AssignTargetMarkerToReticleTarget")
```

どちらかが true、問い合わせ自体ができない、問い合わせがエラーになる、関数が無い、のいずれでも
**呼ばない**。そのときはチャットに理由を1回だけ出し、`/pbtarget status` にも理由が出る。

1.1.0 を PS5 で動かしたユーザーから「表示された」と報告があった（2026-10-20）。ただし 1.1.0 には、
ゲームが許さなかった場合の代替（名前の前に自前のアイコンを出す）があったため、**どちらの経路で表示されたかは
確認できていない**。`/pbtarget status` の `game marker:` が `allowed` なら標準マーカーの経路、それ以外なら
代替だったことになる。1.2.0 では代替を撤去したため、`allowed` でない場合は何も表示されない。

## 名前の照合

名前の表示は「プライマリ名」設定で変わる（`zo_primaryplayername.lua`）: @アカウント名
(`GetUnitDisplayName`)、コンソールID (`GetUnitPlatformDisplayName`)、キャラクター名
(`GetUnitName`、末尾に `^Fx` の性別サフィックス)。**三つとも照合する**ことで、登録するときに
どの名前を入力しても効くようにした。大文字小文字、先頭の `@`（全角 `＠` も）、前後の空白（全角空白も）、
性別サフィックスは無視する。

## 実機で確かめるべきこと

`/pbtarget status` に判断材料を出してある。

1. **マーカーが相手に残るか。** 登録プレイヤーを一度見て、レティクルを外したあとも、頭上にマークが出続けるか。
   これが「視界に入った時点で表示される」の実質的な答えになる。
2. **付けられない相手がいるか。** 「ターゲットマーカーを付けられない対象です」が出る相手（敵プレイヤー、
   ソロ時など）。`last contact:` に出た文言を教えてほしい。
3. **マーカーが他のプレイヤーに移る様子。** 複数人を登録したとき、最後に見た1人に移ること。

## 倒れて別の場所で復活したとき、登録外の人にマーカーが付く（1.6.1 で対策）

報告: マーカーが付いたプレイヤーが死亡し、別の場所でリスポーンすると、その人の死亡地点の近くにいる、登録外の
プレイヤーにマーカーが付いてしまう。

**原因（アドオン側）。** `AssignTargetMarkerToReticleTarget` は相手を指定せず、「ゲームが処理する瞬間にレティクルの先
にいる人」に付ける。1.6.0 までのアドオンは、レティクルのイベントが来るたびに「登録プレイヤーなのにマーカーが
無い」と見て付与を依頼していた。

1. 登録プレイヤーが倒れる。レティクルは死体の上。マーカーは死亡で外れる。
2. 死体にもレティクルのイベントが来る。アドオンは「マーカー無し」と判断して付与を依頼する。
3. ゲームが処理するまでの間に、本人はリスポーンして死体は消え、レティクルは死亡地点にいた別の人に移る。
4. その別の人に付く。

テスト（`test/run.lua` の 25 節）で再現できる。死亡の防御を外すと、死体への再付与が起きて失敗する。

**対策。**
- **死んだ相手には付けない。** `IsUnitDeadOrReincarnating("reticleover")` を見る。さらに、キルフィードの被害者と
  `EVENT_UNIT_DEATH_STATE_CHANGED`（レティクルの先限定）で死亡を記録し、10 秒間は付けない。
- **レティクルが落ち着くまで待つ。** イベントの 250 ms 後に、同じ登録プレイヤーがまだ同じ人かを名前で確かめてから
  付ける。違えば取り下げる（`aborted` に数える）。
- **付いてしまったら外す。** 付与の直後（`EVENT_TARGET_MARKER_UPDATE`、3 秒以内）と、登録外のプレイヤーに
  レティクルが当たったときに、その人が「アドオンが付けた種類のマーカー」を持っていて、登録外・グループ外・自分では
  ない場合に外す。外すには `AssignTargetMarkerToReticleTarget(TARGET_MARKER_TYPE_NONE)` を使う。
  条件はさらに絞る: アドオンが 10 分以内にマーカーを付けていること、同じ人には 5 秒に 1 回まで。
- 外す操作が効くかは**未測定**（`NONE` がクリアを意味するかは、ドキュメントからは分からない）。1 秒後に確認して、
  マーカーが残っていたら、そのセッションの除去をやめる（`clearFailed`）。`/pbtarget unmark` は、この測定を手動で行う
  コマンド（外す前・外した 1 秒後を表示）。

**この原因が唯一かは分からない。** 死体への付与は確かに起こるが、別の経路（ゲームが死亡時にマーカーを近くの人へ
付け替える、など）があれば、この対策では防げない。その場合に備えて「付与の直後に外す」「見かけたら外す」を入れて
ある。PS5 で `/pbtarget status` の `stray clean-up:` 行（発見・除去・失敗、死亡を確認した数、死亡のため見送った数、
レティクルが動いて中止した数）を見れば、どの対策が働いたかが分かる。

## 使用者の制限（1.4.0）

使えるのは PSN ID が `SO1-WYLDE` と `PinkBanther` の2名だけ。`GetPlatformDisplayName()` を読み込み時に
照合する（大文字小文字・先頭の `@`・前後の空白は無視）。ESO の `@アカウント名` は見ない。`GetDisplayName()` は
`ZO_SavedVars` が読み込み時に使っているので、ロード時に値が取れることは確かだが、`GetPlatformDisplayName()` が
PS5 で PSN のオンライン ID を返すことは**未測定**。許可された本人が拒否された場合は、`/pbtarget` が読み取った
PSN ID を表示するので、それで切り分けられる。

許可外の場合は、イベント登録・設定パネル・保存変数をすべて作らず、ログイン後に1回だけチャットへ
「あなたはこのアドオンを使用できません」を出す。チャットは `EVENT_ADD_ON_LOADED` の時点ではまだ使えないため、
最初の `EVENT_PLAYER_ACTIVATED` で出す。

この判定は Lua のソースに書かれているため、ファイルを書き換えられる相手には効かない。うっかり使われること、
気軽な導入を防ぐためのもの。

## 設計上の割り切り

設定パネルは「スロット固定（20枠）」にしてある。LibHarvensAddonSettings は行の動的な追加・削除
（`RemoveAllSettings` / `AddSettings`）もできるが、コンソールでの挙動をこのファミリーのアドオンで測った
例が無いため、実績のある部品（サブメニューになるセクション、テキスト入力、ボタン、ボタンからの再描画）
だけで組んだ。

## 経緯（1.1.0 までに実装し、1.2.0 で削除したもの）

ターゲット枠・グループ枠の名前ラベルに、プレイヤーごとの色と四角い枠を付けていた。クライアントが
ラベルの文字を `UpdateName` で書き換え、色を `DoAlphaUpdate` で何度もリセットするため、`SetColor` ではなく
テキストに `|cRRGGBB…|r` を埋め込み、250 ms の巡回で書き換えを検知する作りだった。「書き換えられたか」は
書いた直後の `GetText()` の戻り値と比べる（`GetText` がマークアップを落とすクライアントでも、巡回のたびに
マークが増えない）。枠は色だけの `Texture` 4 本（XML）だった。不要になったので全て撤去した。
